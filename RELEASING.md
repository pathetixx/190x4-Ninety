# Релиз Ninety

Единый счётчик — **semver** в `src-tauri/tauri.conf.json`. Тег = `vX.Y.Z`
(например `v0.1.56`). Схема `v0.1.0-alphaNN` устарела с 0.1.56 — больше не
используем.

**Никакого «alpha» в заголовке релиза и нигде в метаданных.** Заголовок =
`Ninety vX.Y.Z`, чисто. Фаза проекта (alpha) — наше внутреннее знание, юзера она
бесит. `prerelease` тоже **false** (см. ниже почему).

## Одной командой

Весь пред-CI ритуал (шаги 1–5 ниже) делает `scripts/release.mjs`. Ручные
переменные ровно две — **номер версии** и **заметки** — каждая авторится один
раз: версия аргументом, заметки секцией `CHANGELOG.md`. Скрипт разложит их без
рассинхрона (заметки → аннотация тега → тело draft'а, теми же байтами).

```
# 1. дописать секцию в начало CHANGELOG.md:
#    ## v0.1.96 — 2026-07-06
#    - что нового…
# 2.
node scripts/release.mjs 0.1.96 --watch
```

Делает: читает заметки из верхней секции CHANGELOG (падает, если её версия ≠
аргументу), бампит 4 файла, коммитит в `main`, ставит аннотированный тег через
`-F`, пушит `main` + тег, создаёт draft-релиз тем же текстом. С `--watch` дальше
находит CI-ран по SHA коммита, ведёт его до конца (`gh run watch`, компиляция →
проверка → GitLab promotion → публикация) и проверяет исход: релиз published и не prerelease, есть
`.exe`/`.sig`/`.msi`/Full Portable ZIP/`latest.json`, а `latest.json` реально отдаётся с GitHub
(`/releases/latest/`, версия совпала ⇒ релиз Latest) и с GitLab (первичный
источник). До публикации draft CI загружает и проверяет immutable installer и
versioned metadata GitLab, затем переключает `stable/latest.json`. Красный CI до
этого шага оставляет обе стабильные точки на предыдущем релизе; красный CI на
предварительных стадиях оставляет draft неопубликованным. Катим fix-forward.

Флаги: `--watch` — довести через CI и проверить OTA; `--verify` — только прогнать
эти проверки на уже вышедшем релизе (`node scripts/release.mjs 0.1.96 --verify`);
`--yes` — без вопроса-подтверждения перед push'ем тега; `--dry-run` — показать
план без записей и сети; `--allow-branch` — разрешить не из `main`.

Ниже — что скрипт делает пошагово (и как сделать вручную при разборе поломки).

## Шаги

1. Бамп версии — одной командой (проставляет одно значение во все 4 файла:
   `tauri.conf.json`, `Cargo.toml`, `Cargo.lock` пакет `ninety`, `package.json`):
   ```
   node scripts/bump-version.mjs X.Y.Z
   ```
   Механизм чтения версии Tauri не централизуем (`"../package.json"` сломал бы
   греп версии в `build.yml` → latest.json/OTA); скрипт синхронизирует все места.
2. Добавить секцию в `CHANGELOG.md` — тем же текстом заметок, что пойдёт в тег
   (шаг 4). Новая версия ставится **сверху**, формат заголовка `## vX.Y.Z —
   YYYY-MM-DD`:
   ```
   ## v0.1.96 — 2026-07-06

   <тот же текст, что в -m тега / --notes draft'а>
   ```
   `CHANGELOG.md` — читаемая история для репозитория, зеркало OTA-заметок (как в
   BetterDiscord). Единый текст в трёх местах: CHANGELOG ↔ аннотация тега ↔ тело
   draft'а — не разъезжаться.
3. Коммит в `main` (бамп версии + CHANGELOG), push.
4. Тег **обязательно аннотированный**, сообщение тега = заметки релиза. Push
   тега запускает релизную сборку:
   ```
   git tag -a v0.1.56 -m "Что нового в этой версии…"
   git push origin v0.1.56
   ```
   > **Почему -a с заметками (критично для OTA).** Шаг "Generate latest.json"
   > берёт `notes` для `latest.json` (= changelog в OTA-окне) с приоритетом из
   > **аннотации тега**, тело релиза — лишь фолбэк. Лёгкий `git tag v0.1.56`
   > (без -a) даёт `%(contents)` = сообщение коммита (напр. «v0.1.80») → именно
   > оно уедет в OTA вместо changelog'а. Сообщение тега, секция `CHANGELOG.md`
   > (шаг 2) и `--notes` draft'а (шаг 5) должны совпадать.

   > Сразу тег + релиз, **без** предварительного `workflow_dispatch` «на проверку»
   > — даже когда менялся Rust. Релизный билд сам и есть проверка компиляции;
   > красный → fix-forward следующим тегом. Две компиляции = пустая трата
   > раннер-минут. (`workflow_dispatch` оставлен в триггерах только для ad-hoc
   > отладки CI, не для релизного ритуала.)
5. **Сразу** создать GitHub Release **как DRAFT** с заголовком и заметками
   (тем же текстом, что в аннотации тега — это тело страницы релиза и фолбэк):
   ```
   gh release create v0.1.56 --draft --title "Ninety v0.1.56" --notes "…"
   ```
   **Заголовок указываем сами** (без «alpha»!): softprops при публикации draft'а
   имя НЕ перезаписывает (проверено на 0.1.60 — без --title вышло голое
   «v0.1.56»).

   > **Почему DRAFT (критично для OTA).** Updater-эндпоинт —
   > `releases/latest/download/latest.json`, редирект на релиз с бейджем
   > **Latest**. Если создать релиз сразу published, он мгновенно становится
   > Latest, а `latest.json`-ассет появится только через ~12 мин (когда CI
   > закончит) → всё это время `/latest/latest.json` отдаёт **404** → у ВСЕХ
   > апдейтер молчит «обновлений нет». Драфт исключён из Latest: пока идёт билд,
   > `/latest/` указывает на ПРЕДЫДУЩИЙ рабочий релиз (OTA жива), а CI-шаг
   > "Release on tag" (softprops, `draft:false` по умолчанию) публикует draft
   > вместе с ассетами в самом конце → переключение без слепой зоны. Бонус:
   > упавший билд оставляет draft неопубликованным — OTA не ломается вообще.
6. Дождаться зелёного рана (`gh run watch`). CI проверяет Windows artifacts и
   запуск приложения, обновляет R2 для legacy-клиентов, безопасно продвигает
   GitLab и только затем публикует draft + грузит GitHub assets. Проверить: релиз стал published и Latest, есть
   `Ninety_X.Y.Z_x64-setup.exe` (+`.sig`), `.msi`, Windows x64 Full Portable ZIP,
   `latest.json` с верной
   `version`/подписью, и `curl -sIL .../releases/latest/download/latest.json`
   даёт 302→200 (не 404).

## Почему prerelease: false (не трогать)

Updater-эндпоинт (`tauri.conf.json`) —
`https://github.com/pathetixx/190x4-Ninety/releases/latest/download/latest.json`.
Это редирект на релиз с бейджем **Latest**, а GitHub исключает из Latest всё
помеченное prerelease. Если выставить `prerelease: true`, `/releases/latest/`
начнёт отдавать старый `latest.json` → OTA сломается. Поэтому в `build.yml`
жёстко `prerelease: false` + `make_latest: "true"`.

## Версия vs тег у клиента

Апдейтер сравнивает установленную версию с полем `version` в `latest.json`
(оно берётся из `tauri.conf.json`), а **не** с именем тега. Имя тега —
только git-указатель и контейнер релиза с ассетами.
