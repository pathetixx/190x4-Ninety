# Квалификация Stable-релиза Ninety

Этот документ — ручной gate перед снятием метки `Early access`. Автоматическая
сборка подтверждает компиляцию, unit/regression-тесты, структуру артефактов,
metadata OTA и безопасный запуск приложения, но не заменяет проверку реального
Windows, драйверов, UAC, обновления и SmartScreen.

## Условия начала

- [ ] P0/P1-блокеры исправлены и regression-тесты зелёные.
- [ ] `Checks` зелёный на `main`.
- [ ] Ручной `Build Ninety` через `workflow_dispatch` зелёный.
- [ ] В `src/lib/build-info.js` всё ещё указано `channel: "Early access"`.
- [ ] Релизный тег не создаётся до завершения этой матрицы.

Для каждого ручного пункта сохранить: версию Windows, тип установки, права
пользователя, ожидаемый/фактический результат и ссылку на диагностику. Нельзя
использовать production-профили с секретами в скриншотах и логах.

## Системный proxy

- [ ] До первого запуска proxy выключен: Ninety не меняет его до включения режима `Системный прокси`.
- [ ] До первого запуска включён внешний proxy: `ProxyEnable`, `ProxyServer`, `ProxyOverride` не меняются.
- [ ] До первого запуска включён `127.0.0.1:8080` без маркеров Ninety: все три значения остаются прежними.
- [ ] Ninety включает свой proxy и штатно выключается: предыдущие значения полностью восстановлены.
- [ ] Ninety аварийно завершён: следующий запуск восстанавливает предыдущие значения.
- [ ] После включения Ninety другое приложение меняет proxy: Ninety не перетирает новое значение.
- [ ] Повреждённый/частичный snapshot Ninety не отключает чужой proxy.
- [ ] Legacy snapshot от поддерживаемой старой версии восстанавливается консервативно.

## Режимы, UAC и автозапуск

- [ ] `Прокси`, `Системный прокси`, `VPN · TUN` подключаются и отключаются.
- [ ] Переключение режимов во время подключения не оставляет процессов и системных настроек.
- [ ] Отмена UAC возвращает понятную ошибку и не зависает.
- [ ] `Всегда от администратора` включается/выключается и не создаёт цикл перезапусков.
- [ ] Автозапуск создаётся и удаляется на быстрой и нагруженной системе.
- [ ] Автозапуск после входа скрывает окно и поднимает только ожидаемые функции.
- [ ] Путь задачи обновляется после OTA и корректен для пробелов/Unicode.

## Протоколы и sidecar-процессы

- [ ] Обычный профиль sing-box.
- [ ] WARP.
- [ ] XHTTP через xray.
- [ ] NaiveProxy.
- [ ] TrustTunnel.
- [ ] Несколько NaiveProxy-нод одновременно: отдельные `naive-PORT.log`.
- [ ] Несколько TrustTunnel-нод одновременно: отдельные `trusttunnel-PORT.log`.
- [ ] Агрегированный просмотр и очистка логов компонента.
- [ ] Занятые loopback-порты приводят к безопасному выбору других портов или понятной ошибке.
- [ ] Падение sidecar и sing-box отображается и запускает ограниченный reconnect.
- [ ] Reconnect прекращается на установленном лимите и не образует бесконечный цикл.

## DPI

- [ ] Старт/остановка обычного и Monkey mode.
- [ ] WinDivert загружается и выгружается без остаточного драйвера.
- [ ] Подписанный канал обновляется; версия и стратегия меняются ожидаемо.
- [ ] Повреждённая подпись отвергается.
- [ ] При отсутствии сети используется валидный cache, повреждённый cache не принимается.
- [ ] Обновление Ninety после использования DPI не оставляет процесс/драйвер старой версии.

## Kill switch — экспериментальная функция

До отдельного подтверждения на реальных машинах маркировка функции в UI должна
оставаться экспериментальной.

- [ ] Включение/выключение в режимах `Прокси` и `Системный прокси`.
- [ ] После падения sing-box при запущенном Ninety блок остаётся активным до
  переподключения, ручного отключения Kill Switch или выхода из приложения.
- [ ] После штатного отключения VPN блокирующие WFP-правила удаляются.
- [ ] После выхода или аварийного завершения самого Ninety dynamic WFP-session
  удаляется Windows и не оставляет компьютер без сети.
- [ ] LAN allow on/off, DHCP, IPv4 и IPv6.
- [ ] Профили xray, NaiveProxy и TrustTunnel.
- [ ] Перезапуск BFE/Windows Firewall обнаруживается, а policy переармируется.
- [ ] При `Прокси/Системный прокси ↔ TUN` подтверждённый block-all сохраняется
  до readiness нового runtime и снимается только после готовности целевого TUN.

## Строгий туннель и защищённый браузер

- [ ] До старта sing-box ставится preconnect WFP barrier; без него соединение
  не запускается.
- [ ] После готовности TUN policy разрешает трафик через `ninety-tun`, а LAN,
  IPv6 и прямые пользовательские правила не работают.
- [ ] Исчезновение закреплённой ноды не приводит к Auto/fallback на другую ноду
  или прямое соединение.
- [ ] Падение ядра сохраняет fail-closed policy; ручное отключение снимает её.
- [ ] Mullvad Browser нельзя запустить или скачать через Ninety без активного
  `VPN · TUN`.
- [ ] Из elevated Ninety браузер стартует с обычным интерактивным токеном, а не
  с правами администратора.
- [ ] Отключение Ninety не закрывает уже открытый браузер; этот сценарий явно
  проверен и понятен тестировщику.

## OTA: GitLab, GitHub и R2

Релизный порядок: immutable installer GitLab → проверка размера/SHA-256 →
versioned metadata → проверка → `stable/latest.json` → проверка → публикация
GitHub draft как Latest. R2 обновляется для старых клиентов до promotion.

- [ ] Ошибка до promotion оставляет старый GitLab `stable/latest.json` рабочим.
- [ ] Ошибка GitLab оставляет GitHub Release в draft.
- [ ] GitLab stable указывает на существующий versioned installer той же версии.
- [ ] GitLab и GitHub metadata содержат одинаковую updater signature.
- [ ] GitLab — первый endpoint актуального клиента; GitHub работает как fallback.
- [ ] Старый клиент с R2 endpoint получает рабочий updater artifact.
- [ ] Повторный запуск workflow той же версии идемпотентен.
- [ ] Обновление с предыдущей и через несколько версий проходит на реальной машине.

## Authenticode и SmartScreen

Tauri `.sig` — minisign-подпись updater artifact. Она защищает OTA, но не
является Windows Authenticode. Без production Authenticode `Ninety.exe`, NSIS и
MSI могут показывать предупреждение Windows/SmartScreen.

Workflow поддерживает условную production-подпись. Добавить оба GitHub Actions
secret одновременно:

- `WINDOWS_SIGNING_CERTIFICATE_BASE64` — production PFX в Base64;
- `WINDOWS_SIGNING_CERTIFICATE_PASSWORD` — пароль PFX.

При наличии secrets сертификат импортируется во временное хранилище runner,
Tauri получает thumbprint, SHA-256 и timestamp URL, а smoke-step требует статус
`Valid` у `Ninety.exe`, NSIS и MSI. При отсутствии secrets сборка остаётся
зелёной, явно сообщает `production certificate не настроен` и не имитирует
подпись self-signed сертификатом. Настройка соответствует официальной схеме
[Tauri для Windows code signing](https://v2.tauri.app/distribute/sign/windows/).

- [ ] `Get-AuthenticodeSignature` возвращает `Valid` для `Ninety.exe`.
- [ ] `Get-AuthenticodeSignature` возвращает `Valid` для NSIS installer.
- [ ] `Get-AuthenticodeSignature` возвращает `Valid` для MSI.
- [ ] Timestamp присутствует и подпись валидна без сети после истечения сертификата.
- [ ] SmartScreen проверен на чистой Windows 10 и Windows 11.

- [ ] Windows 10 qualification пройдена.
- [ ] Windows 11 qualification пройдена.
- [ ] Upgrade qualification пройдена.
- [ ] Proxy recovery qualification пройдена.
- [ ] TUN/DPI/WFP qualification пройдена.
- [ ] OTA GitLab/GitHub/R2 qualification пройдена.
- [ ] Authenticode status подтверждён.

Только после всех пунктов заменить в `src/lib/build-info.js` (файл собирает
`scripts/gen-build-info.mjs`, но `channel` он переносит из текущей версии —
ручная правка переживает сборку, остальные поля перезаписываются пинами):

```js
channel: "Early access",
```

на:

```js
channel: "Stable",
```

Смена канала должна быть отдельным маленьким коммитом. Затем владелец добавляет
секцию `CHANGELOG.md` и запускает `node scripts/release.mjs X.Y.Z`. Скрипт
завершается на создании draft'а и за сборкой не следит; результат билда
проверяется отдельно — `node scripts/release.mjs X.Y.Z --verify`.
